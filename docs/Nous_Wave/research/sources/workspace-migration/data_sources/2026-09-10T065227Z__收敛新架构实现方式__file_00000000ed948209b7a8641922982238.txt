对，这次我把它从“核心语法实验”升级成了一个较完整的 **NousQL v0.2 capability-complete design draft**。

最重要的修正是：自然语言查询没有消失，而且现在正式成为一等 Query Atom。当前 Nous Wave 本身就已经有 `TextCue`、`ExampleCue`，同时还有 Entity、Object、Artifact、MediaRegion、Tag、Anchor、Relation、Resource 等 cue；约束层还包含 source、memory class、entity、occurred/observed/valid time、authority、modality、evidence class；高级查询还有 topology exploration、current-authority resource intent、effort、result need 和 diagnostics。NQL 如果不能覆盖这些，就不能算 Nous 的 AI query language。fileciteturn30file0 fileciteturn31file0

这版有几个关键变化。

首先，自然语言采用明确的 semantic cue：

```text id="tu8tpm"
~"Rust lifetime errors caused by borrowed values escaping scope"
```

它自己就是完整查询。

也能与结构化焦点结合：

```text id="zy69uz"
@e("Alice") && ~"graduation and moving to Tokyo"
```

这里表示 Alice 是硬焦点，而且结果还必须满足该自然语言语义。

如果只是希望这个语义影响排序：

```text id="v7kkp7"
@e("Alice") +(~"graduation and moving to Tokyo")
```

因此三种东西严格不同：

```text id="xofy48"
@e("Alice") && #school
```

hard intersection。

```text id="p81ynp"
@e("Alice") +(#school)
```

soft preference。

```text id="8ztd5g"
@e("Alice") #school
```

非法，没有隐式 AND。

这正好落实你前面强调的“集合操作、作用域、参数表达必须明确”。

Tag / Anchor 也正式回来了，而且我认为**必须暴露**。架构已经明确说 Tags 是 typed/provenanced cognitive topology primitives，Anchors 是 explicit/revisioned cognitive landmarks，并且 Topological retrieval 本身就是 Exact/Semantic/Topological/Resource/Runtime 五类认知寻址之一。它们不是数据库内部索引细节。fileciteturn28file0

于是：

```text id="ewffhs"
#school
```

是 semantic concept。

而：

```text id="39vf6s"
@tag("school")
```

是确切的 persisted Tag。

这两者永远不允许自动互相转换。

同理：

```text id="fqdc0m"
@anchor("first-year-university")
```

是确切 Anchor，并且自身就有默认 bounded neighborhood cognition：

```text id="lfgosj"
@anchor("first-year-university")
```

已经有意义。

需要继续做关联扩张：

```text id="pcynur"
@anchor("first-year-university") $explore
```

Tag 也是一样：

```text id="l8euct"
@tag("school") $explore
```

这样模型不用每次机械写“around anchor”。

Association 也处理了，不过这里没有假装它和 Tag/Anchor 一样。当前 `CognitiveRef` 有 `Tag` 和 `Anchor`，却没有通用 `Association` reference；与此同时 `ExplorationIntent` 有 `ExplainAssociation`。所以目前更合理的是把 Association 暴露成**查询操作**而不是假装有一个 `@association(id)` 对象。fileciteturn30file0 fileciteturn31file0

高级候选语法：

```text id="1vhkyu"
$assoc(
  a=@ref(mem:amber-lotus-cello-river),
  b=@anchor("first-year-university")
)
```

实际 canonical 会保持单行：

```text id="2024dj"
$assoc(a=@ref(mem:amber-lotus-cello-river),b=@anchor("first-year-university"))
```

意思明确：

> 解释这两个 cognition endpoints 之间的 association。

它和：

```text id="vp64xt"
@ref(mem:...) && @anchor(...)
```

完全不同。后者只是集合交。

另外，我现在把 selector 体系收紧了，不再为所有 CognitiveRef 类型创造几十个缩写：

```text id="18dmkh"
@e(...)          Entity
@tag(...)        exact Tag
@anchor(...)     exact Anchor
@r(...)          Resource
@object(...)     Host-owned external object
@ref(...)        uncommon exact CognitiveRef
```

例如：

```text id="wsy0r2"
@ref(mem:amber-lotus-cello-river)
@ref(obs:quiet-piano-mint-cloud)
@ref(art:coral-frame-lake-bird)
@ref(region:mint-lake-cello-frame)
```

这样不需要教 LLM：

```text id="a81d6b"
@m
@mr
@a
@sr
@dr
@occ
...
```

这符合我们“不把内部对象分类全部泄露给模型”的哲学。

高级约束现在也开始覆盖真实系统能力，比如：

```text id="9pf30o"
@e("Alice") $memory $occurred(within="30d")
```

这是“事情发生在最近 30 天”。

而：

```text id="jf5cgo"
@e("Alice") $memory $observed(within="30d")
```

是“Subject 在最近 30 天观察到”。

还有：

```text id="8a45rw"
$valid(at="2026-09-10T12:00:00Z")
```

是 validity axis。

因为当前系统本身就严格区分 `occurred / observed / valid`，NQL 不能为了短而重新把它们压成一个含糊 `$within`。fileciteturn31file0

其他真实高级能力现在可以写：

```text id="qai1ar"
$source("message","file")
$excludeSource("tool")

$modality("text","image")

$authority("evidence")

$memoryClass("specific","integrative")
$excludeMemoryClass("procedural")

$evidenceClass("direct")

$effort(deep)

$limit(5)

$materialize

$diagnostics(full)
```

例如：

```text id="q4cl57"
@e("Alice") $memory $occurred(within="30d") $source("message","file") +(recent) $limit(5)
```

这里顺序不是“按文字执行”：

```text id="tgsi16"
$memory
$occurred(...)
$source(...)
+(recent)
$limit(...)
```

都是 typed attachments。

系统按照固定 semantic phases 解释：

```text id="2bkkjh"
domain/view
→ hard constraints
→ topology/resource policy
→ soft preferences
→ effort
→ ranking
→ result shaping
→ enrichment
```

即使 parser 接受 attachment 的其他排列，最终 canonical serializer 会重新输出统一顺序。

但**作用域绝不会自动改写**。

例如：

```text id="k69o85"
@e("Alice") || (@e("Bob") $memory)
```

只让 Bob branch 走 Memory specialization。

而：

```text id="wvpra1"
(@e("Alice") || @e("Bob")) {$memory}
```

Memory 作用于整个 union。

类似：

```text id="ekbe8g"
(@e("Alice") $limit(5)) || (@e("Bob") $limit(5))
```

是每个 branch 各取 5。

而：

```text id="35f52d"
(@e("Alice") || @e("Bob")) {$limit(5)}
```

是 union 后全局取 5。

这才是“顺序和作用域明确”，而不是逼模型死记 token 顺序。

关系方向的问题也在完整版里正式引入了“复杂功能必须显式 role”的原则。

普通关系：

```text id="k4b2bk"
@e("Alice","Bob") $relation
```

没有方向，只是 joint Relationship cognition。

如果是：

> Alice trusts Bob

不能偷偷规定“第一个参数就是 source”。

高级形式暂定：

```text id="nxm81u"
$rel(from=@e("Alice"),to=@e("Bob"),kind="trust")
```

这比：

```text id="ogh4fq"
@e("Alice","Bob") $relation("trust")
```

更长，但不会出现最危险的隐含顺序语义。

也符合：

> 高频简单场景尽量缺省；复杂、容易误解的情况宁愿多写一点，把角色写清楚。

还有一个比较重要的边界修正：**NQL 不应该“做到 Nous Wave 的所有功能”。**

正确目标是：

```text id="b91jjs"
NQL
≈ capability-complete Cognitive Query language
```

而不是：

```text id="fmlfdz"
NQL
≈ universal Nous shell
```

例如这些不属于 NQL：

```text id="vsshv7"
RecordObservation
UploadArtifact

FormMemory
ReviseMemory
ConsolidateMemory
SuppressMemory
RestoreMemory
PurgeMemory

CreateTag
CreateAnchor
CreateAssociation
RebindEntity

Open/Close Session
Focus lifecycle
ReportUse
config mutation
```

这些是 Authority mutation / lifecycle / ingestion，应继续走 typed Client API。

另一方面，当前查询 API 中的 provider mechanics：

```text id="uydn56"
text_embedding
text_rerank
residual_sensing
```

虽然目前存在于 `CapabilityPolicy`，我也没有直接映射成：

```text id="y8g0cv"
$embedding
$rerank
$residual
```

因为这会违反项目自己的原则：公开 Cognitive Query 应表达 semantic effort/capability needs，不应暴露具体 retrieval algorithm / provider mechanics。仓库的 AGENTS 也明确要求 public Cognitive Query 不暴露 implementation-specific algorithm fields。fileciteturn27file0

因此 NQL 里让模型说：

```text id="sc7f7p"
$effort(deep)
```

而不是：

```text id="ugum78"
$useDense
$rerank
$wave
```

planner 决定怎么满足它。

还有一个很适合解决“完整语言 vs few-shot 不能太长”的机制：**Capability-Gated Vocabulary**。

完整语言可以很丰富，但给某个 LLM 的使用说明只列当前可用能力，例如：

```text id="vq4cf2"
domains: memory
topology: tag, anchor, association
resources: yes
relation: unavailable
persona: unavailable
diagnostics: summary
```

当前架构明确 Persona/Social/Epistemic/Goals/Reflection/Diary/Dream 都还是 FUTURE，不应该为了 NQL 语法完整就创建假实现。fileciteturn28file0

所以未来实现 Social 后，可以注册：

```text id="ees5tc"
$relation
```

实现 Persona 后注册：

```text id="x73ljz"
$persona
```

语法本身不用升级。

但没有 capability 时，LLM quick reference 根本不教它这个词。

这可以同时做到：

```text id="58jcmf"
Full NousQL
很完整

LLM few-shot
仍然很短
```

我认为 v0.2 已经可以作为后续正式语言 prototype 的基础了。下一轮最值得做的不是继续添 keyword，而是用这份新的 Quick Reference 给多个模型做一轮明显更难的测试，重点攻击：**自然语言 + 结构化 cue 混合、Concept vs exact Tag、Anchor topology、branch/group scope、时间三轴、Resource current authority、复杂 directional relation**。如果这些也能稳定通过，我们就可以开始真正写 grammar/parser prototype，而不再只停留在纸面设计。
