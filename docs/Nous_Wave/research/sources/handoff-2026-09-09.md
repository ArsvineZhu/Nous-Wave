## 2. User Directives

- Treat Nous Wave as a large, evolving research/prototype system. Do not assume the current architecture is final merely because it exists.
- Preserve the project engineering posture:
  - Library-first / Anti-NIH.
  - Avoid overengineering, maintenance bureaucracy, unnecessary TDD/gates/frameworks.
  - PRE_PRODUCTION permits direct rewrites; there is no compatibility/legacy obligation unless a real external obligation exists.
  - Mature low-maintenance tooling is desirable when it lowers total maintenance burden.
- Do not reopen the already accepted architecture baseline casually. The current corrective closure should fix concrete semantic/runtime gaps rather than trigger another Foundation Reset / Architecture Rebase.
- The currently executing corrective closure plan should not be interrupted or modified unless the user explicitly asks later.
- Subject semantics:
  - `Subject != Model`
  - `Subject != Agent`
  - `Agent != Persona`
  - a Subject is distributed across multiple agents/models/processes.
- Do not globally inject Persona or other cognition into every consumer. Different agents may have different system-prompt cores and different cognitive needs.
- A Session may have its own cognitive maintainer/Steward; do not assume one giant global Agent maintains all Subject state.
- The Steward / projection model should preferably be a cheap, fast, long-context model (Flash/Spark-class profile) if possible; flagship reasoning models would unnecessarily increase latency for factual projection/stewardship.
- Nous is not traditional RAG. Retrieval latency is not the only or necessarily primary objective in advanced modes; higher-quality managed cognition may deliberately pay additional latency.
- Even with LLM-enhanced operation, basic functionality and graceful degradation must remain. LLM failure/unavailability must not make Nous unusable; deterministic/basic retrieval must remain.
- Memory maintenance / Dreaming-like functions should not require a hidden autonomous scheduler. Prefer public APIs and/or write-time/query-time/Host-triggered maintenance; expensive LLM-dependent maintenance requires configured model capability.
- LLM output remains proposal-first and must be validated before becoming cognitive Authority.
- Automatic Tag/Anchor/Association generation may use model assistance, but should remain a capability, not a globally autonomous Agent.
- Agent-facing access should not be raw structured API only. Internally use typed queries/ASTs, but agents should have a concise dedicated Nous cognitive query language.
- Do not copy unstable literal search syntax such as `+(term)` or `--QDF=5` as the internal core protocol; learn the underlying concepts (boosting, freshness, precision/recall probes).
- Configuration principle: **first make meaningful runtime policy uniformly configurable, then decide whether to expose it to end users**. `Configurable != user-configurable`.
- Avoid unexplained hard-coded runtime policy values. Prefer typed configuration owners and resolved configuration snapshots.
- Programming language choice is explicitly reopened. Rust-only is no longer a default virtue.
- Current preferred language direction is provisional:
  - Rust for high-performance / transactional / serving / retrieval kernel responsibilities.
  - TypeScript-first for model/provider orchestration, Steward, Projection Runtime orchestration, Managed Context, Agent Query Language, configuration resolution, and likely Persona/Relationship orchestration.
  - Python remains research/experimentation by default, not a third production runtime unless a real need appears.
- Do not force “one physical exe” if that harms architecture. One product may contain multiple languages/processes and still ship as one application bundle/installer.

## 4. Decisions & Rationale

- **Decision:** Accept the current Architecture Rebase baseline; do not roll it back.
  - **Why:** The deep review found the ownership rebase, Character Seed, Serving lifecycle, runtime ordering, ConsumerWorkingSet, governance, and several correctness fixes to be real improvements.
  - **Alternatives rejected:** another Foundation Reset / another Architecture Rebase.
  - **Status:** confirmed
  - **Source:** joint conclusion

- **Decision:** Close remaining defects through a bounded Corrective Closure wave rather than another architecture rewrite.
  - **Why:** Remaining problems are primarily “declared semantic/type exists but runtime path does not actually consume it” and lifecycle correctness gaps.
  - **Alternatives rejected:** another giant conceptual Spec/reset.
  - **Status:** confirmed
  - **Source:** joint conclusion

- **Decision:** `Subject != Model`, `Subject != Agent`, `Agent != Persona`.
  - **Why:** Heptalogos may enact one Subject through multiple agents: expression, operator, planning, research, etc.
  - **Alternatives rejected:** one Subject = one Agent; one global Persona projection for all consumers.
  - **Status:** confirmed
  - **Source:** user

- **Decision:** Consumer projection must be role-sensitive, not merely token-budget-sensitive.
  - **Why:** Different agents have different system-prompt cores and cognitive needs; e.g. Persona may be required for expression but irrelevant/noisy for machine operations.
  - **Alternatives rejected:** globally broadcasting current Persona/Subject state to every consumer.
  - **Status:** confirmed
  - **Source:** user + joint conclusion

- **Decision:** Active Cognition should be richer than a flat ResidentSet.
  - **Why:** Subject-stable cognition, focus/task cognition, working knowledge, and ephemeral execution state have different lifetimes and projection semantics.
  - **Alternatives rejected:** one scalar resident/activation concept as the only model.
  - **Status:** provisional
  - **Source:** joint conclusion

- **Decision:** Focus should become a meaningful runtime primitive.
  - **Why:** Switching tasks/topics should switch foreground cognition while allowing suspended focus checkpoints and dropping disposable execution detail.
  - **Alternatives rejected:** treating Session as one undifferentiated active context.
  - **Status:** provisional
  - **Source:** joint conclusion

- **Decision:** A Session-scoped Steward is preferable to one global cognitive-maintenance Agent.
  - **Why:** It avoids cross-task contamination, giant context, and focus interference.
  - **Alternatives rejected:** one Subject-wide giant Steward.
  - **Status:** provisional
  - **Source:** user + joint conclusion

- **Decision:** Steward is not cognitive Authority.
  - **Why:** Its model context is a replaceable projection; Session runtime state must survive model/provider/window changes.
  - **Alternatives rejected:** making the Steward prompt/context the sole copy of active state.
  - **Status:** confirmed
  - **Source:** joint conclusion

- **Decision:** Prefer a cheap, fast, long-context Steward/factual projector where possible.
  - **Why:** The primary job is faithful active-knowledge projection and factual recall, not frontier-level reasoning; flagship models add latency/cost.
  - **Alternatives rejected:** defaulting all internal cognition to the strongest model.
  - **Status:** provisional
  - **Source:** user

- **Decision:** Projection is shared cognitive infrastructure, not Memory-specific.
  - **Why:** Persona, Relationship, Goals, Epistemic, Resources, and future MicroSystems will also need consumer-specific projection.
  - **Alternatives rejected:** separate bespoke projection agent per subsystem.
  - **Status:** confirmed direction
  - **Source:** user + joint conclusion

- **Decision:** Keep both Assistive Cognition and Managed Cognition.
  - **Why:** Third-party agents may only support tool/query integration, while tightly integrated Heptalogos agents can allow Nous/Host to manage the model-visible context directly.
  - **Alternatives rejected:** making one mode exclusive.
  - **Status:** provisional
  - **Source:** joint conclusion

- **Decision:** Managed Context should be treated as explicit context compilation, not hidden-CoT manipulation.
  - **Why:** Providers such as DeepSeek accept caller-constructed message histories; hidden CoT is not a reliable or portable architectural dependency.
  - **Alternatives rejected:** designing around hidden chain-of-thought access.
  - **Status:** confirmed
  - **Source:** user correction + joint conclusion

- **Decision:** Context management should be cache-aware and epoch/generation-oriented.
  - **Why:** Provider prompt/KV caches depend on stable prefixes; arbitrary full prompt rewrites every turn destroy cache locality.
  - **Alternatives rejected:** freely reshuffling/rebuilding all prompt content every turn; simplistic sliding-window deletion as the only strategy.
  - **Status:** provisional
  - **Source:** joint conclusion

- **Decision:** Semantic correctness outranks cache preservation.
  - **Why:** Cache is physical optimization; materially stale Persona/instructions/focus cannot be retained merely to preserve prefix hits.
  - **Alternatives rejected:** preserving semantically obsolete prefixes for performance.
  - **Status:** confirmed
  - **Source:** joint conclusion

- **Decision:** LLM assistance must be optional; Nous must degrade gracefully.
  - **Why:** Advanced projection/maintenance may fail or be unconfigured, but stored cognition, Authority correctness, provenance, and basic retrieval must remain.
  - **Alternatives rejected:** LLM-required availability.
  - **Status:** confirmed
  - **Source:** user

- **Decision:** Dreaming/maintenance should be invoked through public API and/or write-time/query-time/Host-triggered maintenance rather than requiring a hidden autonomous scheduler.
  - **Why:** The user wants explicit controllable semantics and configuration, not mandatory periodic background behavior.
  - **Alternatives rejected:** scheduler-first architecture.
  - **Status:** confirmed
  - **Source:** user

- **Decision:** Model output remains proposal-first before Authority mutation.
  - **Why:** LLM synthesis can hallucinate and must pass semantic validation/provenance rules.
  - **Alternatives rejected:** model output directly becoming Authority.
  - **Status:** confirmed
  - **Source:** joint conclusion

- **Decision:** Agent-facing Nous access should have a dedicated query language that compiles to typed AST/query operations.
  - **Why:** Agents benefit from concise expressive syntax, while code needs structured, validated semantics.
  - **Alternatives rejected:** exposing only raw structured API; using unstable leaked syntax as internal protocol.
  - **Status:** confirmed direction
  - **Source:** user

- **Decision:** `Configurable != user-configurable`; meaningful runtime policy should be configurable before product exposure is decided.
  - **Why:** Nous/Heptalogos will have many internal policy knobs; hard-coding them makes later tuning and productization difficult.
  - **Alternatives rejected:** scattered constants; exposing all internal tuning knobs directly to users.
  - **Status:** confirmed
  - **Source:** user

- **Decision:** Rust-only is no longer the default language policy.
  - **Why:** high-performance/transactional kernel code and fast-changing model/control-plane code have different engineering requirements; Coding Agent iteration speed is a legitimate architecture variable.
  - **Alternatives rejected:** “important code must be Rust”; rewriting all working Rust into TS.
  - **Status:** confirmed reopening of decision; exact split remains provisional
  - **Source:** user + joint conclusion

- **Decision:** Leading language direction is `Rust Cognitive Kernel + TypeScript Cognitive Host`.
  - **Why:** Rust remains strong for Authority/transactions/serving/retrieval/kernels; TS is more suitable for provider/model orchestration, Steward, Managed Context, query language, configuration, and high-change cognition orchestration.
  - **Alternatives rejected:** Rust-only as default; TypeScript-only rewrite.
  - **Status:** provisional
  - **Source:** assistant recommendation accepted in discussion, not yet formally locked by user

- **Decision:** One product does not require one physical executable.
  - **Why:** source language, compilation unit, runtime process, distribution artifact, and user-facing product are separate concerns.
  - **Alternatives rejected:** forcing architecture around a single `.exe`.
  - **Status:** provisional
  - **Source:** joint conclusion
