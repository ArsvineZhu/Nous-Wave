CandidateSemanticTrail 仍然会制造“有序语义路径”

这里不需要马上研究新理论，可以先采用成熟、清楚的 representative subset 方法，例如 deterministic farthest-point / kmeans++-style seeding / clustering medoids，或者把此算法保持 DEFAULT 并补真实 adversarial test。

Derivation fencing 仍有并发正确性问题

真正的 fence 应该在 commit semantic result 之前。

update derivation
finish attempt
COMMIT

值得研究，而且我认为这批新信息对 Nous Wave 的价值高于再研究一个新的向量库或图算法。它直接碰到了我们现在最核心的三个问题：长任务连续性、长期记忆形成、以及“模型如何主动检索自己的历史/外部数据”。

先给结论：OpenAI 现在实际上已经把“上下文、任务历史、长期记忆”拆成了三套不同机制。这个分层和 Nous Wave 当前架构高度同构，而且有几个设计值得直接吸收。

1. 先把 OpenAI 现在的三层东西分开
层	OpenAI 当前做法	Nous Wave 对应
当前模型可见上下文	Codex Context Window / token budget / new_context	ConsumerWorkingSet / ContextContribution
同一任务的长期连续性	persisted thread history + notes/checkpoint + history retrieval	Session + ResidentSet，以及尚未明确实现的 continuation/checkpoint
跨任务长期认知	Codex local Memory / ChatGPT Dreaming	Nous Memory MicroSystem
最重要的一句话是：

Context compression != Memory formation
Task handoff != durable Memory
History retrieval != reinforcement
Context rollover != forgetting
Summary != Authority
这正是 Nous Wave 应该继续坚持的方向。

2. Codex 其实经历了两代完全不同的“压缩”
第一代：真正的 compaction
这是现在已经比较成熟的方案。

早期 Codex 的 /compact 很传统：

完整历史
→ 让模型总结
→ 用 summary 替换历史
→ 接着工作
后来 Responses API 加了原生 /responses/compact。它不再只是生成一段人类可读摘要，而会生成特殊的 compaction item，其中包含不透明的 encrypted_content，用于保留模型对之前状态的“latent understanding”。Codex 会在达到阈值后自动调用它。

OpenAI 从 GPT-5.1-Codex-Max 开始甚至专门训练模型跨多个 context window 工作。官方说它能在单任务中连贯处理数百万 tokens，内部测试出现过超过 24 小时的任务。

这已经给我们一个重要提示：

Compaction artifact 可以是 provider/model-specific acceleration state，而不必是人类可读 Memory。

映射到 Nous：

ProviderCompactionState
    = Model Cache / provider-specific derived runtime state

不是
    Memory
    Session Authority
    Cognitive Authority
未来如果 OpenAI、Anthropic 或其他 provider 提供这种 opaque compaction token，Nous 完全可以保存、复用，但它应该属于 Model Cache / derived continuation artifact，不能成为 Subject 连续性的唯一依赖。

3. 但最近推出的 Experimental Context Management 更有意思
Codex 0.153.x 新加入：

[features.context_management]
experimental_mode = true
符合条件的 ChatGPT Plus/Pro/Pro Lite + Codex backend 会得到三样东西：

token-budget context
history notes
new_context
这是官方 release 明确写出的组合。

而源码中的 new_context 工具描述非常直白：

“Start a new context window. Does not clear, reset, or otherwise affect environment state.”

也就是：

重置模型看到的窗口
≠
重置任务
≠
重置环境
更关键的是，新 token-budget compaction 的源码注释明确说明：

它会跳过 model/server summarization，直接安装一个新的 context window。

这已经不是传统意义的“摘要压缩”了。

4. 新方案本质上是“换窗 + 外部状态”，而不是“递归总结”
从 Codex 源码看，新 window 有自己的：

first context window id
current context window id
previous context window id
而真正开始新窗口时，它会重新构造 initial context / world state，并保留某些 developer messages，而不是继续把完整旧消息塞进模型。

所以它的思路更接近：

               ┌─────────────────────────┐
               │ Persistent task history │
               │ tool results / messages │
               │ notes / checkpoints     │
               └────────────┬────────────┘
                            │ search/read
                            ▼
Window #1 ──checkpoint──> Window #2 ──checkpoint──> Window #3
    │                         │
    └──── environment ────────┴──── unchanged
不是：

Window #1
  ↓ summarize
Summary #1 + Window #2
  ↓ summarize
Summary #2 + Window #3
  ↓ summarize
Summary #3 ...
后者有很严重的 recursive summarization loss：

raw fact
→ summary
→ summary of summary
→ summary of summary of summary
每轮都会丢信息，而且错误会固化。

新思路则允许：

checkpoint = 当前任务状态的小型索引/摘要
history    = 仍然存在的原始历史
需要细节时再检索 history。

这一点非常值得 Nous Wave 吸收。

5. 为什么它可能显著提高模型效率
用户社区说“效率大涨”并不奇怪，但目前我没有看到 OpenAI 给这个实验 Context Management本身公布一个“提升 X%”的正式数字，所以这里不能把体感当 benchmark。

机制上，它确实能大幅降低浪费。

A. 不再每次推理都背着整个历史
传统 agent loop 每个 inference 都会重复发送越来越长的 prompt。OpenAI 自己在 Codex agent-loop 文章中明确把这个称为核心性能问题，并且特别强调 prompt cache hit。

新模式相当于：

旧：
100k history
+ 2k current
→ inference

新：
5k task state/current window
+ retrieve 3k relevant history if needed
→ inference
这对 attention 成本、prefill、cache、模型注意力污染都有明显好处。

B. 不再频繁调用模型做全局 summarization
源码明确说 token-budget rollover skip model/server summarization。

这不只省一次模型调用。

它还避免：

让主模型读 100k
→ 生成 5k summary
→ 下一窗口再不断携带 5k summary
C. 原始历史变成“按需查”
这是类似虚拟内存的思路：

current working set     RAM
historical thread       backing store
notes/checkpoint        page table / working index
当然我们不要在项目文档里真把它称作虚拟内存——这里只是说明机制。

关键变化是：

“曾经发生过”不再意味着“每次 inference 都要重新读取”。

这与 Nous 的：

stored
resident
working
projected
used
分层完全一致。

6. 不过 Codex 这套实验实现现在还有很严重的问题
这也是为什么我建议学习设计，不照搬 lifecycle。

就在 9 月 6–8 日，已经有真实 bug：

一种情况：

notes checkpoint 写成功
→ new_context
→ 新窗口没有 restore checkpoint
→ Agent 忘记正在做什么
→ “你好，需要我帮你做什么？”
另一种：

notes 写失败
→ new_context 仍然执行
→ 任务状态直接丢失

这个 bug 对 Nous 的启发反而非常直接。

Nous 不应该允许模型自己通过一句“我记好了”来完成 context handoff。

正确生命周期应该由 controller 强制：

PrepareContinuation
        ↓
persist checkpoint
        ↓
verify persistence
        ↓
switch context window
        ↓
restore checkpoint
        ↓
verify active-task continuity
        ↓
allow normal inference
失败：

checkpoint failed
    → DON'T switch

restore failed
    → rollback / fallback compaction
这应该是原子/有 fence 的状态转换。

不是现在正在执行的 Corrective Spec 里加。

把它记成下一轮研究候选即可。

目前我们有：

Session
ResidentSet
ConsumerWorkingSet
ContextContribution
local WorkCycle
Memory
缺少的是：

Context Window Continuation
可以是类似：

ContextWindowId

ContinuationCheckpoint {
    session,
    previous_window,
    objective,
    current_state,
    active_refs,
    unresolved_items,
    recent_tool_outcomes,
    continuation_hints,
    provenance,
}
注意它的身份应该是：

Runtime-derived state
而不是：

Memory
它可以保存很久以便恢复 Session，但它描述的是：

“这个任务做到哪里了”

不是：

“Subject 学到了什么”。

例如：

“query.rs 已拆完，下一步正在修 field-dense”
是 task continuation。

而：

“用户长期偏好 library-first，允许大重构”
才可能进入长期 cognition。

两者必须分开。

8. Codex 自己也确实把长期 Memory 单独做了
OpenAI 现在已经正式文档化 Codex Local Memory。

它跟 context management 是另一套东西。

Codex 会把符合条件的旧聊天后台加工成本地 memory 文件，而且：

跳过仍在进行的 session；

等聊天 idle 一段时间后才生成；

rate-limit 较低时可以跳过生成；

有单独的 thread extraction model；

有单独的 global consolidation model。

更值得注意的是它保存的不是单一 summary，而是：

summary
persistent entries
recent inputs
evidence from previous chats

这非常合理。

它实际上在避免：

Memory = 一个越来越长的 profile summary
而变成：

Memory state
├─ synthesized summary
├─ durable items
├─ recent raw-ish context
└─ supporting evidence
这跟 Nous 当前：

Memory
MemoryRevision
Evidence
ObservationOccurrence
DerivedRepresentation
Integrative Memory
非常接近。

9. 一个尤其值得注意的 Codex 规则
OpenAI 官方 Codex Memory 文档明确提醒：

必须遵循的团队规则应该放在 AGENTS.md 或版本控制文档里；Memory 只是辅助回忆，不应该成为必须遵循规则的唯一来源。

这实际上验证了我们一直在强调的 Authority 问题。

对 Nous：

Host / external Authority
    ↓
当前项目规则 / 当前事实

Nous Memory
    ↓
Subject 对这些信息的认知和回忆
不能：

Memory recalled "probably X"
→ X 就变成当前世界真相
所以这条 research transfer 我认为可以直接标成 PRESERVED。

10. ChatGPT 的 Dreaming 更值得研究长期 Memory
2026 年 6 月 OpenAI 公布了 Dreaming V3。

它已经不是旧式 Saved Memories：

聊天中遇到 “记住 X”
→ 写一条 memory
而是后台：

many conversations
      ↓
background synthesis
      ↓
current memory state
      ↓
continually updated
OpenAI 明确把目标定义成三类：

carry forward useful context；

follow preferences/constraints；

stay current over time。

第三条尤其重要。

它甚至会做：

未来：
“用户七月要去新加坡”

时间过去：
“用户 2026 年七月去过新加坡”

这说明它的 Memory 不只是 append-only fact extraction，而包含：

temporal reinterpretation
state evolution
staleness correction
这与我们研究 A-MEM / Graphiti 后想给 Nous 建立的：

new experience / passage of time
→ evaluate current cognition
→ revision / integration
高度一致。

11. 而且你说的“效率提升”在 ChatGPT Memory 上确实有官方数字
OpenAI 说 2026 Dreaming 架构显著提高了计算效率，并且近期改进把向 Free 用户提供 Dreaming 所需的 compute 降低了约 5 倍。

这跟 Codex Context Management 的“效率大幅提升”不要混在一起：

Dreaming
≈ 官方明确约 5x serving compute improvement

Experimental Codex Context Management
≈ 机制上明显更节省上下文，但我没找到官方量化 X 倍
这是两个不同数字。

12. ChatGPT 还有一个很好的设计：Memory Summary 不是 Memory 本体
OpenAI 明确说：

Memory Summary 应该包含最重要的信息，但不会包含 ChatGPT 所记得的一切。

并且回复下面的 Memory Sources 可以告诉用户这次用了哪些：

custom instructions
past chats
files
memories
但 Sources 也不保证显示影响回复的全部因素。

这对 Nous 很有价值。

未来不要做：

Persona.md
MemorySummary.md
=
认知 Authority
更好的结构是：

Cognitive Authority
        ↓
Memory Summary Projection
        ↓
human review / UI
Memory Summary 是一种 Serving / Human Inspection Projection。

用户可以改它，但修改动作最终应该转换成有 provenance 的 Authority mutation，而不是直接把 Markdown 当数据库。

13. 再说你注意到的 +(关键词)
这个很有意思。

我找到的公开资料中，OpenAI 官方用户/API 文档并没有把 +(foo) 声明为 ChatGPT 面向用户的搜索语法。

官方 Chat History Search 当前反而还明确写着：

标题和内容按关键词/短语搜索，目前主要支持 exact matches。

7 月 14 日的新 Unified Search 则把：

chats

14. 不过 +(...) 确实在公开流传的工具提示材料里出现了
几个第三方公开仓库保存的 ChatGPT/file-search prompt material 中，确实出现：

+term
+(multi word entity)
语义是：

boost 包含该 term/phrase 的 retrieved documents。

而且还出现：

--QDF=0 ... --QDF=5
即 Query Deserved Freshness，用于告诉检索器这次查询有多重视新鲜度。

例如其描述大致是：

+(John Doe)
+(File Service)
--QDF=0   historic/stable
...
--QDF=5   latest
但是这里必须严格区分：

这些是第三方收集/泄漏性质的材料，不是 OpenAI 稳定公开 API 文档。

所以我不会建议 Nous 去兼容：

+(foo)
--QDF=5
这个具体字符串协议。

15. 真正值得学习的是它背后的 Retrieval Query Planning
这比 + 字符本身重要得多。

模型收到：

“找我最近谈 Nous Wave Context Management 的内容”

它内部不一定只搜一次：

Nous Wave Context Management
更合理的 planner 会生成多个 probe：

Precision:
+(Nous Wave) +(Context Management) -- recent

Recall:
context management

Semantic:
context rollover continuation checkpoint

Temporal:
last few days

Scope:
past chats / project files
然后汇总。

这与我们当前 CognitiveQuery → QueryPlan 很契合。

我会建议 Nous 下一阶段引入一个内部 Retrieval Intent Compiler：

CognitiveQuery
      ↓
QueryPlan
      ↓
RetrievalIntentCompiler
      ├─ ExactProbe
      ├─ PrecisionLexicalProbe
      ├─ RecallLexicalProbe
      ├─ SemanticProbe
      ├─ TopologySeeds
      ├─ ResourceProbe
      └─ Freshness / Time constraints
而不是让所有 backend 自己理解用户原始一句话。

16. 甚至不需要做字符串 DSL
不要实现：

"+(Nous Wave) --QDF=4"
作为内部核心协议。

直接 typed：

struct RetrievalProbe {
    text: String,
    boosts: Vec<BoostTerm>,
    freshness: FreshnessPreference,
    time_range: Option<TimeRange>,
    source_scope: SourceScope,
    mode: RetrievalMode,
}
然后：

Tantivy adapter
    → 编译到 Tantivy query

USearch
    → embedding + ANN

Postgres exact
    → typed SQL

ResourceResolver
    → provider-native query

history store
    → history-native query
这样更加符合：

semantic intent
!= physical query syntax
也正符合我们现在给 EPA/Wave 做的算法 seam 思路。

17. QDF 的思想可以吸收，但 0–5 不一定应该吸收
QDF=0..5 很像一个 Search Engine ranking feature。

它对 file/search retrieval 非常实用，因为：

“Rust ownership 是什么”
不要求最近。

但：

“Rust 最新 stable 是什么”
高度要求最近。

Nous 当前 CognitiveQuery 已经有 temporal/resource semantics，所以可以更加类型化：

FreshnessPreference::Stable
FreshnessPreference::Recent
FreshnessPreference::Current
FreshnessPreference::Latest
或者更直接：

preferred_age
required_after
valid_at
而不是把一个神秘 3 存进 cognitive Authority。

因为：

QDF = retrieval planner hint
不是：

cognitive property

19. 还有一个很重要的性能启发：stable prefix
Codex 官方的 agent-loop 文章反复强调 prompt cache hit，并且配置发生变化时尽量追加一个新 message，而不是回头修改旧 prompt，因为修改早期内容会破坏 cache prefix。

这对 Nous 的 ContextContribution 很值得研究。

未来 projection 可以自然分为：

StablePrefix
├─ Subject identity
├─ authoritative instructions
├─ stable capability context
└─ stable project/resource descriptors

DynamicWorkingSet
├─ current task
├─ recent observations
├─ recalled cognition
└─ current resources
再加：

EphemeralTurn
这样可以显著提高 provider prompt caching。

但仍然要记住：

Prompt Cache
= Model Cache
不能因为某个 provider 的 cache strategy 改变，就改变 Nous 的 cognitive semantics。

最重要的研究结论
我现在反而会进一步强化 Nous Wave 原来的一个设计判断：

Memory 系统不是“把模型上下文做大”的手段。

真正高效的系统应该让：

Cognitive Authority       很大
Historical evidence       很大
Memory                    很大

ResidentSet               较小
ContinuationCheckpoint    很小
ConsumerWorkingSet        很小
Current model context     有严格预算
然后通过高质量 retrieval，把当前真正需要的极少部分投影给模型。

OpenAI 最近 Codex 的 Context Management、Codex Local Memory、ChatGPT Dreaming、Unified Search，实际上正越来越明显地朝这个方向汇合。

我认为等当前 Corrective Closure 执行结束后，下一轮最值得做的已经不是继续填 Memory CRUD，而是专门研究一个 Cognitive Runtime Continuation + Retrieval Intent Compilation 波次；它能把 Codex 的长任务换窗、ChatGPT 的记忆召回、我们已有的 Session/ConsumerWorkingSet 和 VCP 式认知检索真正整合到一起。


我同意重新决定，而且现在比项目早期更适合决定，因为 Nous Wave 已经自然分化出两类完全不同的工作负载。继续坚持“整个系统都是 Rust”开始变成一种人为约束，而不是架构优势。

当前 workspace 的 Rust 栈集中在 PostgreSQL/SQLx、Tantivy、USearch、petgraph、OpenDAL、embedded PostgreSQL、并发 serving 等领域；apps/nous-wave 本身已经同时承担 Axum API 和 Clap CLI。 另一方面，我们最近新增的方向——Projection Runtime、Session Steward、Managed Context、模型 capability routing、Agent Query Language、配置解析、Persona/Relationship 编排——恰好都是变化快、LLM/JSON 密集、性能要求低于检索核心、Coding Agent 修改频繁的代码。

所以我目前最看好的不是改成 TypeScript，而是：

Nous Wave
=
Rust Cognitive Kernel
+
TypeScript Cognitive Host
而且两者应该是明确的 coarse-grained boundary。

│ deterministic projection fallback                    │
│ existing Memory transactional invariants             │
└──────────────────────────────────────────────────────┘
这比：

everything = Rust
合理，也比：

everything = TypeScript
合理。

2. Rust 应该保留，但不再承担“所有重要代码”
这一点需要避免另一个误区：

“重要的就用 Rust，不重要的用 TS。”

不对。

语言边界应该看：

performance characteristics
failure semantics
data ownership
change frequency
library ecosystem
development friction
而不是业务重要性。

比如 Persona 极其重要，但它很多逻辑可能是：

LLM proposal
→ structured validation
→ revision decision
→ projection
根本没有理由为了“重要”而写成 Rust。

相反，一个完全不具有高层认知意义的：

ANN candidate scan
可能非常适合 Rust。

3. 哪些现有 Rust 代码我不会搬
现在正在执行的 Corrective Closure 完成后，我不会建议把已经正确工作的 Rust Memory 系统重写成 TS。

尤其：

authority-store
object-store
serving
memory-retrieval
material / material-service 的高性能路径
继续 Rust。

MemoryService 目前也大量涉及：

transaction
revision
purge reachability
projection invalidation
derivation fencing
已经付出了很高的正确性成本。

现在搬语言属于没有收益的大重写。

因此策略应该是：

Existing correct Rust stays Rust; new components are no longer Rust-by-default.

这和 PRE_PRODUCTION 允许重构并不冲突。允许重构不等于有理由就重写。

4. 新功能我反而会默认 TypeScript
尤其是下面这些。

Session Steward
非常明显：

prompt
model call
structured output
tool call
retry/degradation
context construction
TS 比 Rust 更自然。

Managed Context
需要大量操作：

messages[]
provider payload
reasoning item
tool result
cache metadata
context contributions
token budgets
本质上就是高度动态的结构化数据处理。

TS 非常适合。

Provider / model capability routing
这类代码以后更新会极频繁：

OpenAI
Anthropic
Google
DeepSeek
local provider
...
模型 API 也不停变化。

这里 Rust 的编译期严格性带来的收益远小于修改摩擦。

Agent Query Language
Parser 本身 Rust 当然可以写。

但：

Agent language
→ AST
→ query planning
→ projection request
→ tool interaction
整个上层都在 TS 时，把 parser 单独放 Rust 没什么价值。

Configuration
尤其我们刚讨论的：

unified config
resolved config
provider config
consumer profiles
projection config
context policy
TS 对 schema transformation 和大量 typed configuration 非常友好。

5. Coding Agent 的开发能力确实应该算架构变量
这不是“迁就 AI”。

Nous Wave 的现实开发主体就是 Coding Agent + 人类架构控制。

Rust 的问题不在于 Agent 不会写 Rust。现在最强的 Coding Agent 显然会。

问题在于：

改一个认知策略
→ 类型变化
→ lifetime / trait bound
→ async Send
→ borrow ownership
→ compile
→ 修十几个 crate
对于真正需要 Rust 保证的组件，这笔成本值得。

但对于：

projection policy
prompt composition
provider adapter
configuration
Steward protocol
query language
就很不划算。

TS 下 Coding Agent 可以更加快速地：

inspect
modify
run
test
iterate
而且整个 AI 应用生态本身对 TS/JS 的支持极强。

所以：

Agent development velocity 本身应该进入 language-selection cost model。

这和我们反对 AI 过度工程其实是同一个思想。

6. Python 我反而不建议成为第三种生产主语言
Python 非常适合 Nous 的：

algorithm experiments
research
evaluation
benchmarks
data exploration
notebooks
prototype model integration
但我目前不建议：

Rust + TS + Python
三种都成为 production runtime。

原因不是 Python 性能，而是：

packaging
environment management
dependency conflicts
typing boundary
async runtime
deployment
会额外产生很多成本。

所以初步语言政策可以非常简单：

Production:
    Rust
    TypeScript

Research / experimental:
    Python
如果以后某个真正成熟的 ML library 只有 Python，那再增加一个 isolated Python worker。

不是现在预先建 Python architecture。

7. “Nous Wave 必须是一个 exe”本身就应该重新审查
这里你说得对。

需要区分四个概念：

source language
≠ compilation unit
≠ runtime process
≠ distributable product
完全可以：

source:
    Rust + TypeScript

runtime:
    2 processes

distribution:
    1 application bundle / installer

user:
    sees one Nous Wave
这在工程上非常正常。

我们没必要为了：

ls
nous-wave.exe
只有一个文件，而强行让十万行逻辑都用 Rust。

8. 不同语言当然能组成一个产品，但“编译成一个 exe”有几种不同含义
方案 A：两个进程，一个安装包
这是我目前最推荐的。

nous-host
    TypeScript runtime

nous-kernel
    Rust native binary
然后：

Heptalogos
→ starts nous-host
→ nous-host starts/connects nous-kernel
用户根本不需要知道有两个进程。

优点：

边界清晰；

Rust crash 不直接摧毁 TS VM；

TS model/provider bug 不污染 DB process；

kernel 可以独立运行；

degradation 很自然；

Rust CLI/API 仍然可用；

容易开发、调试；

不受某个 JS FFI ABI 强绑定。

这也是我当前第一候选。

9. 进程之间的 typed boundary 现在甚至有一个很值得研究的新方案
ConnectRPC / Protobuf。

就在 2026 年 8 月 26 日，Anthropic 把他们开发的 connect-rust 正式贡献给了 Connect 项目；现在官方 Rust 实现支持 Connect、gRPC、gRPC-Web，并直接集成 Tower/Axum。

而 TypeScript 侧已有 Connect-ES，Buf 可以从同一个 Protobuf schema 生成 TS 类型和 service stub。

这和 Nous 非常匹配，因为当前 Rust app 本来就在使用 Axum。

可以变成：

proto/
  cognitive.proto
  session.proto
  authority.proto
  projection.proto
  config.proto

              schema
              /    \
             /      \
        Rust         TypeScript
          │              │
      nous-kernel ←──→ nous-host
不是说现在立刻应该上 Protobuf。

但它值得作为第一候选 qualification。

尤其这个库源自 Anthropic 自己的生产需求，这对 Agent 系统这个场景是个很好的信号。

10. 第二种：NAPI-RS，把 Rust 直接作为 TS native addon
也完全可行：

TypeScript
    │
    ▼
@napi
Rust
napi-rs v3 当前可以直接把 Rust 类型/函数暴露给 JS，并生成 TypeScript declarations；Node-API 本身提供跨后续 Node 版本的 ABI 兼容性。

使用体验可以做到类似：

import {
  query,
  materialize,
  commitMemory,
} from "@nous/kernel";
底下实际上是 Rust。

这对 Coding Agent 极友好。

11. 但我暂时把 NAPI-RS 放第二候选
因为 Nous Kernel 不是一个简单算法库。

它拥有：

PostgreSQL
serving lifecycle
background-ish runtime resources
object store
Tokio
HTTP/CLI
large native indexes
把整个 Kernel 压进 Node process 以后：

Node lifecycle
+ Tokio lifecycle
+ native addon lifecycle
+ crash boundary
+ packaging
会耦合起来。

而我们本来又希望：

No LLM
No TS host
时仍然能降级运行基本 Nous。

因此独立 Rust kernel process 更符合我们前面定下的：

Intelligence is an enhancement layer, not an availability prerequisite.

12. “一个真正的 exe”也不是做不到
现在 TS 已经有成熟的 standalone distribution。

Deno deno compile 可以把 TS/JS 和运行时打成 self-contained native executable，并支持 Windows/macOS/Linux 及 cross-compilation。

Bun 也支持：

compile: true
生成 standalone executable，并可以针对其他平台构建。

Node 26 自己也已经支持：

node --build-sea
构造 Single Executable Application，不过 Node 官方仍把 SEA 标成 Stability: 1.1 - Active development。

所以：

TypeScript != 必须让用户安装 Node
早已经不是事实。

13. 但 Rust + TS 真正合成“一个文件”就没那么自然
可以：

方法 1
TS executable 中嵌 Rust sidecar，首次运行 extract：

nous-wave.exe
├ embedded TS runtime
├ TS application
└ embedded nous-kernel.exe
启动后：

extract
→ spawn kernel
用户看起来还是一个 exe。

Deno 已经有 self-extracting executable 的相关机制，并且其 compile 系统也考虑 native addons。

方法 2
Rust 编译成 .node native addon，通过 NAPI-RS 进入 JS executable。

方法 3
Rust 主程序嵌 V8/JS runtime，然后执行 bundled TS→JS。

其中方法 3 我最不建议。

因为我们会为了“一个文件”主动承担：

embedded JS runtime lifecycle
module loading
runtime upgrades
native module integration
debugging
这完全是 distribution requirement 反过来污染 architecture。

14. WASM 也不适合成为这里的胶水
Rust→WASM→TS 看起来很漂亮：

Rust
→ wasm
→ TypeScript
但我们的 Rust Kernel 有：

SQLx/Postgres
Tantivy
USearch
filesystem
native object storage
threads
embedded PostgreSQL
这些东西不适合为了 WASM 被重新适配。

WASM 可以以后用于：

plugin
portable algorithm
sandboxed extension
而不是当前 kernel boundary。

A. TypeScript Host ↔ Rust Kernel

B. TypeScript Host ↔ Rust Kernel

我当前明显偏向 A。尤其 Connect 的 Rust 实现刚刚由 Anthropic 贡献进官方项目，并原生支持 Axum，而我们的 Kernel 已经在 Axum 上，这个时间点相当合适。

这样既保住 Rust 在该用的地方的优势，也终于停止让 Rust 去承担它并不擅长、而 Coding Agent 又会频繁修改的大量认知编排代码。
